# `M(2,2,2,4)` plus rational `3`-torsion

This tests the roomier base family

```text
C: y^2 = x(x+a^2)(x+b^2)(x+c^2)(x+d^2),
```

which has visible torsion containing `[2,2,2,4]` on the nonsingular open
chart.  The goal is to impose an independent rational `3`-torsion class, using
the same cubic-contact equations as in the `M(2,2,2,8)+3` computations.

The reusable script is

```text
code/m2224_plus3_search.m
```

It supports:

```text
magma -b mode:="finite" code/m2224_plus3_search.m

magma -b mode:="search" height:=80 prime_bound:=37 point_prime_bound:=73 \
    max_exact:=10 code/m2224_plus3_search.m

magma -b mode:="exact_file" tuple_file:="data/file.txt" \
    code/m2224_plus3_search.m
```

## Finite-field diagnostic

The finite mode scans the good affine `M(2,2,2,4)` chart over finite fields and
intersects it with the coefficient keys admitting a degree-2 cubic-contact
`3`-torsion divisor.

The first run showed:

```text
p 5:  good_points 0
p 7:  good_points 0
p 11: good_points 1920,    contact_points 1920
p 13: good_points 5760,    contact_points 0
p 17: good_points 26880,   contact_points 6144
p 19: good_points 48384,   contact_points 13824
p 23: good_points 126720,  contact_points 33792
p 29: good_points 384384,  contact_points 75264
p 31: good_points 524160,  contact_points 178560
p 37: good_points 1175040, contact_points 335232
```

Thus `p=13` is the first genuine good-reduction obstruction for rational
`3`-torsion on this base.  The primes `5` and `7` are not meaningful open-chart
filters here because there are too few nonzero square classes to have four
distinct branch-square residues.

## Integer tuple pilots

The search mode scans primitive positive sorted tuples and, by default, keeps
only tuples with bad reduction at `13`.  It then applies cubic-contact residue
filters at good primes up to `prime_bound`, followed by a point-count gcd bound
before any exact `TorsionSubgroup` call.

Height `50`, `prime_bound=31`:

```text
checked           215659
boundary13        163821
contact_survivors 11658
no3_bound         11658
survived_bound    0
exact             0
hits              0
```

Height `80`, `prime_bound=37`:

```text
checked           1473833
boundary13        1153263
contact_survivors 48698
no3_bound         48698
survived_bound    0
exact             0
hits              0
```

So the larger `M(2,2,2,4)` base does give many more contact-filter survivors
than the tight `M(2,2,2,8)` K3 chart, but the later good-prime point-count gcd
bound kills every tested integer tuple before exact torsion.

## Early point-count residue filter

I then moved part of the point-count obstruction earlier.  The search now has a
separate `point_prime_bound` parameter.  For primes above the cubic-contact
filter, it precomputes the good-chart coefficient keys for which
`3 | #J(F_p)`.  Tuples that are good at one of these primes but miss this table
are rejected before the rational curve is constructed and before the full gcd
bound is run.

Validation with `height=50`, `prime_bound=31`, `point_prime_bound=43` gave:

```text
checked           215659
boundary13        163821
contact_survivors 11658
point_survivors   1347
no3_bound         1347
survived_bound    0
exact             0
hits              0
```

The stronger height-`80` pilot with `prime_bound=37`, `point_prime_bound=73`
gave:

```text
checked           1473833
boundary13        1153263
contact_survivors 48698
point_survivors   36
no3_bound         36
survived_bound    0
exact             0
hits              0
```

Thus the early point-count residue filter is doing the intended CRT-style
pruning: in the height-`80` box it cuts the post-contact population from
`48698` to `36` before the full rational gcd-bound step.


## Component-wise `p=13` boundary analysis

The component-wise finite analysis is implemented in

```text
code/m2224_plus3_boundary13_analysis.m
```

with output

```text
data/m2224_plus3_boundary13_analysis.txt
```

It labels the `p=13` boundary components as

```text
Zi:   i-th coordinate is 0,
Eij+: ai = aj,
Eij-: ai = -aj.
```

It solves the raw monic cubic-contact equations over `F_13`, allowing bad
cover reduction.  The main counts are:

```text
base_total                 28561
open_base                   5760
boundary_base              22801
contact_solutions          43680
open_contact_solutions     13824
boundary_contact_solutions 29856
cover_open_solutions        3936
```

The `open_contact_solutions` are all degenerate: their cover signature is
`gcd(q,f)`, matching the earlier good-reduction obstruction.  The genuinely
nondegenerate `cover_open` contacts occur only on the boundary.

Component-wise, every collision component `Eij+` and `Eij-` has nondegenerate
contacts:

```text
for each Eij±:
  base_points             2197
  bases_with_contact       696
  contact_solutions       2160
  bases_with_cover_open    216
  cover_open_solutions     432
```

Pure zero components are different.  The pure signatures `Z1`, `Z2`, `Z3`,
`Z4` have only `gcd(q,f)` contacts, with no `cover_open` contacts.  Zero
components acquire nondegenerate contacts only on intersections with collision
components or deeper zero strata.

The first-order lift check is implemented in

```text
code/m2224_plus3_boundary13_lift.py
```

with output

```text
data/m2224_plus3_boundary13_lift.txt
```

It linearizes the three eliminated contact equations modulo `13^2` at the
`cover_open` boundary contacts.  The result is:

```text
cover_open_boundary_solutions 3936
p2_liftable                   3552
all_boundary_labels_first_order 3552
```

Thus the component-wise `p=13` analysis does not locally kill the route.  The
live branches are real first-order `13`-adic branches, especially the pure
collision components and the zero/collision intersections.  The obstruction
seen in the height searches comes from compatibility with later good-prime
point-count conditions, not from the individual `p=13` boundary components.


## Residue-driven `13`-boundary enumerator

The live first-order `p=13` residue bases are generated by

```text
python3 code/m2224_plus3_live13_residues.py \
    --out data/m2224_plus3_live13_residues.txt
```

This produced

```text
live_residue_bases 1776
```

The residue-driven integer enumerator is

```text
code/m2224_plus3_residue_enum.m
```

It reads the live ordered `p=13` residue bases, loops over integer triples
`a<b<c`, generates only `d` values in live `p=13` residue classes, and then
applies good-prime point-count and cubic-contact residue filters before writing
tuple rows.

A height-`80` run through point-count primes up to `73` was:

```text
magma -b height:=80 point_prime_bound:=73 \
    output_file:="data/m2224_plus3_residue_H80_p73.txt" \
    progress_interval:=100000 code/m2224_plus3_residue_enum.m
```

It found:

```text
checked_triples    82160
live_triples       35900
live_d_candidates  89908
point_survivors    6
unique_rows        6
```

The six tuples were:

```text
[3,41,62,74]
[3,54,56,62]
[11,24,35,52]
[12,23,40,70]
[22,36,55,63]
[26,35,47,69]
```

Feeding this file to the exact/contact checker gave:

```text
magma -b mode:="exact_file" \
    tuple_file:="data/m2224_plus3_residue_H80_p73.txt" \
    prime_bound:=37 point_prime_bound:=73 max_exact:=10 \
    code/m2224_plus3_search.m
```

with result:

```text
tuples            6
boundary13        6
contact_survivors 0
point_survivors   0
survived_bound    0
exact             0
hits              0
```

So the residue-driven enumerator is working as intended: it reduces the
height-`80` search to six arithmetically plausible tuples before the full
contact checker, and those six are eliminated by the cubic-contact filters.

I then moved the same strict cubic-contact residue filters directly into the
residue enumerator, while keeping the point-count filters active at all good
primes, including contact primes.  The run

```text
magma -b height:=80 point_prime_bound:=73 contact_prime_bound:=37 \
    output_file:="data/m2224_plus3_residue_H80_p73_c37.txt" \
    progress_interval:=100000 code/m2224_plus3_residue_enum.m
```

gave:

```text
checked_triples    82160
live_triples       35900
live_d_candidates  89908
point_survivors    6
contact_survivors  0
unique_rows        0
```

The contact kills occurred at primes `23`, `29`, and `37`, with counts
`2`, `1`, and `3` respectively.  Thus the residue enumerator now reproduces
the exact/contact checker's elimination of the six height-`80` point-count
survivors before writing any rows.

## Current interpretation

This remains a sensible pivot, but the first broad integer boxes are negative.
The individual `p=13` boundary components are not locally impossible: many
nondegenerate boundary contacts lift to `13^2`.  After forcing this boundary,
however, point-count residues through `p=73` almost completely eliminate the
integer search.  The residue-driven `13`-boundary enumerator is now in place,
and with direct cubic-contact residue filters it writes no height-`80` rows.
The next useful improvement would be a higher-height chunked run with these
filters already active, or a structural explanation of why the later
good-prime point-count conditions are so incompatible with the live `p=13`
boundary branches.

## Live `p=13` boundary filter

I then added a lightweight version of the component-wise `p=13` refinement to

```text
code/m2224_plus3_search.m
```

via the option

```text
boundary13_live_only:=true
```

The component analysis showed that pure zero components `Zi` have no
nondegenerate `cover_open` contacts by themselves; nondegenerate contacts live
on collision components `Eij+`, `Eij-`, and on intersections with those
components.  The new filter therefore keeps only tuples whose branch parameters
have a square collision modulo `13`, rather than merely being bad at `13`.

A height-20 validation run was:

```text
magma -b mode:="search" height:=20 prime_bound:=31 point_prime_bound:=43 \
    boundary13_live_only:=true max_exact:=5 progress_interval:=0 \
    code/m2224_plus3_search.m > data/m2224_plus3_live13_h20_p43.txt
```

It gave:

```text
checked           4619
boundary13        2624
contact_survivors 74
point_survivors   1
no3_bound         1
survived_bound    0
exact             0
hits              0
```

The larger run was:

```text
magma -b mode:="search" height:=120 prime_bound:=37 point_prime_bound:=73 \
    boundary13_live_only:=true max_exact:=20 progress_interval:=1000000 \
    code/m2224_plus3_search.m > data/m2224_plus3_live13_h120_p73.txt
```

It gave:

```text
checked           7627637
boundary13        4950148
contact_survivors 240851
point_survivors   239
no3_bound         239
survived_bound    0
exact             0
hits              0
```

So the live-boundary refinement confirms the earlier obstruction pattern.  The
`p=13` boundary itself is not empty, and many tuples pass the cubic-contact
residue filters through `p=37`; however, once the later point-count filters and
the rational good-prime gcd bound are applied, every height-120 survivor is
killed before exact torsion computation.  This makes blind extension of the
same `M(2,2,2,4)+3` integer box low value.
