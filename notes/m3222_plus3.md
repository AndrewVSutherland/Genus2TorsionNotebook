# `M_1(8,2,2)` / `[2,2,8]` plus rational `3`-torsion

This records the first pass after pivoting from `M(2,2,2,8)+3` to the roomier
odd `M_1(8,2,2)` family.

## Family

Use the existing odd model from the `m3222` scripts:

```text
C_{u,v}: y^2 = f_{u,v}(X),
Q = (-1, u*v*(u+v+1)).
```

The polynomial is

```text
f_{u,v}(X) = ((1-u)X+1)((1-v)X+1)((u+v+2)X+1)
             *(-X^2 + (u^2*v-u^2+u*v^2-u-v^2-v-2)X
                     -(u^2+u*v+v^2+u+v+1)).
```

On the nonsingular open family, the visible rational 2-torsion together with
the distinguished order-8 point gives the expected `[2,2,8]` torsion.

## Search script

I added

```text
code/m3222_plus3_search.m
```

It uses the necessary condition for rational `3`-torsion:

```text
3 divides #J(F_p)
```

at every good prime `p != 3`.  For each prime it precomputes the open residue
classes `(u,v) mod p` satisfying this condition, then scans rational `(u,v)`
and exact-computes torsion only for survivors.

## Height 6 validation

Run:

```text
magma -b height:=6 prime_bound:=43 max_exact:=50 \
    code/m3222_plus3_search.m > data/m3222_plus3_h6_p43.txt
```

The open finite-field condition is already obstructed at small primes:

```text
p=7:  nonsingular=12, allowed3=0
p=11: nonsingular=24, allowed3=0
p=13: nonsingular=48, allowed3=0
```

So rational examples must reduce to boundary at `7`, `11`, and `13`.
Unlike the tighter `M(2,2,2,8)+3` route, boundary survivors do appear quickly.
At height `6`, there were `2` survivors, both exact-checking to only

```text
torsion [2,2,8].
```

## Height 20, primes up to 43

Run:

```text
magma -b height:=20 prime_bound:=43 max_exact:=200 \
    code/m3222_plus3_search.m > data/m3222_plus3_h20_p43.txt
```

Summary:

```text
checked   261121
curve_ok  256938
survivors 1686
exact     200
hits      0
```

The first `200` exact survivors all had torsion `[2,2,8]`.  The surviving
modular gcd bounds were still divisible by `3`, so the prime bound needed to be
strengthened before exact-checking all survivors.

## Component-wise boundary analysis

The open finite-field condition is empty at `p=7,11,13`, so a rational
`[2,2,8]+3` example would have to reduce to boundary at all three primes.  I
then solved the raw cubic-contact equation

```text
h^2 - f = m^2 q^3
```

on all finite `(u,v)` residues, with `q = X^2 + U X + V`, `V = w^2`, and
`S = m w^3`.  This avoids the monic eliminated formulas, since this quintic is
not generally monic.

Run:

```text
magma code/m3222_plus3_boundary_analysis.m \
    > data/m3222_plus3_boundary_analysis.txt
```

Results:

```text
p=7:  contact_solutions=0
p=11: contact_solutions=12, all on boundary, all with gcd(q,f)
p=13: contact_solutions=12, all on boundary, all with w=0, disc(q)=0, gcd(q,f)
```

More explicitly, at `p=11` the only live base components are

```text
delta1=0:    8
s^2-4p=0:   4
```

and every one has `gcd(q,f)`.  At `p=13` the only live base components are

```text
delta2=0:   8
s-p+1=0:   4
```

and every one has `w=0`, `disc(q)=0`, and `gcd(q,f)`.

Since the finite monic `q` chart was completely empty at `p=7`, I also checked
the projective `q=[A:B:C]` chart over `F_7`, including `A=0` pole charts.

Run:

```text
magma code/m3222_plus3_projective_q_p7.m \
    > data/m3222_plus3_projective_q_p7.txt
```

This found

```text
projective_q_points 57
base_open           12
base_boundary       37
solutions           84
bases_with_solution 12
open_qopen          0
```

There are no signatures of the form `open | ...`: every projective `q` contact
at `p=7` lies over a base-boundary residue.  Some of these contacts have
`q_open`, so projectivizing `q` does add boundary contacts missed by the finite
monic chart, but it does not restore an open-base solution at `p=7`.

Current interpretation: the `[2,2,8]+3` route is strongly obstructed.  Any
rational example would have to live in a simultaneous bad-reduction/valuation
chart at `7`, `11`, and `13`, rather than in a straightforward finite
Mumford-contact chart.
